Rules of Thumb
Record every call
Use a passive AI transcript tool (e.g. Krisp AI). Always ask for the recording/transcript before the call ends — rebuild scope from transcript, not memory.
Never assume ingestion channel
EAC inbox vs. Outlook vs. Gmail vs. fax-to-email vs. SharePoint — almost never confirmed on discovery. Flag as explicit SOW assumption. Always nail down the literal endpoint.
Bi-directional = 2 flows
If a customer says "bi-directional" and can't tell you what writes back and when — park it as Phase 2. Exception: closed-won Opp in SF → create SO in QB → write back SO# = one flow.
Cloud vs. on-prem = #1 cost driver
Confirm deployment before pricing connectivity. Cloud vs. on-prem of source/target is the single biggest cost driver — not the data model.
Legacy systems need connector strategy
QuickBooks Desktop, Sage 100, IQMS — needed workarounds (Web Connector, ODBC, file-based polling). Ask if the system exposes REST APIs natively or only legacy protocols.
Template variance multiplies IDP effort
Each vendor PDF template requires its own extraction prompt. Always ask "how many distinct source templates exist?" — not just "what document types?"
Large docs need splitting strategy up front
PDFs >40 pages can run into thousands of pages (EliteExperts case). Custom chunking + monitoring needed. Treat >40-page and bundled files as an architecture decision.
Use this for any deal involving document extraction or classification. Ask every question even if the answer seems obvious — the answer directly changes t-shirt size and price.

Common Source Systems
Email inbox (Outlook / Gmail)
IDP can monitor an inbox directly as the ingestion point.
Scanning device / service
File-creation event triggers IDP processing automatically — useful during a digitization rollout.
Secure document portals
e.g. SecureDocs-style portals — usually require an RPA layer to log in and download on a schedule, since these portals rarely expose a public API.
Existing file server / SharePoint
Used for retroactive/backfill processing of existing documents, plus new incoming documents.
Non-Negotiable Technical Call-Outs
Confidence thresholds & human review: Every IDP scope includes a confidence threshold (e.g. <80%) that routes low-confidence extractions to a human review queue. Always scope this explicitly — it is a distinct configuration line item, not free with extraction.
Deduplication logic: Needed whenever the same document could arrive more than once (fax retries, multi-channel submission). Scope as part of the integration logic, not IDP extraction.
Large-document workaround: For huge files (thousands of pages), expect a custom chunking component (e.g. Mule PDFBox module) plus monitoring/alerting for chunking failures — call this out as its own effort line. It is fragile and needs support.
Additional Discovery Questions
1Any document type legally restricted from AI processing (NDA, regulatory rules)? Flag as out-of-scope / human-only in SOW.
2Ask for volume AND average page count together (e.g. "~1,200 docs/year, ~40 pages average") — both combine to drive effort differently than either alone.
3For every document type, separate "must-have" fields from "nice-to-have" fields — scope an MVP field set, not everything day one.
4Are documents always in one language or multiple languages? Multi-language changes the extraction/OCR model, not just volume.
5How do documents currently arrive — email attachment, portal download, or scanned physical mail? Each has a different ingestion architecture even if the document type is identical.
6Never quote IDP effort without 3–5 real sample documents per distinct format/template variant. A verbal description is not enough.
7Ask what confidence threshold the business is comfortable with AND who operationally owns the human-review queue day to day. A threshold without a named owner is an incomplete scope item.
8Does any inbound file mix a structured form with free-text/handwritten notes in the same doc (hybrid document)? Needs splitting/dual-extraction step — score above a plain structured document.
9If customer has a manual second-person verification step, ask whether they want it preserved as human-in-the-loop post-automation or fully eliminated. This is a business decision, not a technical default.
10Does extracted data need to trigger downstream automation (renewal reminders, compliance flags, approval workflows)? If yes → that logic is Anypoint scope, price separately.
11When an engagement mixes structured/templated sources with unstructured freeform sources, score and price them separately even if the customer calls them "the same document."
12Confirm whether downstream delivery needs full Anypoint Platform or lighter native Salesforce Flow ingestion path. Choosing Anypoint over Flow when Flow would suffice adds ~half-day of avoidable configuration effort.

Additional Discovery Questions
1For every shared entity, ask directly: "which system is the system of record?" Get the answer in writing before building any sync logic.
2What happens if the same record is updated in both systems simultaneously — which system wins? "Bi-directional" is not complete until this conflict-resolution rule is defined.
3Should deletes propagate between systems — hard delete or soft delete/archive flag? Undefined delete behavior = common source of data-loss incidents post go-live.
4Does the source support push-based real-time events (webhooks, Change Data Capture, Platform Events) or must MuleSoft poll on a schedule?
5Ask about API rate limits on both source and target. Confirm whether a separate bulk export exists for the one-time historical data load — a backfill is a distinct effort line from ongoing sync.
6How many environments are needed (Dev/QA/UAT/Prod)? Can the customer provide non-production credentials or sandbox access for testing?
7How should integration failures be handled — silent log, email alert, or retry queue? Who on the customer side owns the error queue?
8Does the integration depend on a third party outside the customer's control (distributor, partner, vendor feed)? Confirm they are aware and have agreed to the timeline.
9Is there a hard external deadline driving the project (board meeting, audit, fiscal year-end)? Capture explicitly — often dictates timeline more than technical complexity.
10For legacy on-prem systems with no REST API, map all connectivity options before defaulting to custom code: ODBC, business-object/COM interface, third-party REST wrapper, flat-file import/export.
11For objects with child/line-item records (invoice lines, order lines), does the target need line-item-level detail or a header-level summary?
12If the customer syncs on a fixed cadence, ask whether that's a deliberate business choice or a limitation of current tooling. Don't assume the new integration should preserve the old cadence.
13Does any personal data crossing systems trigger data-residency or privacy requirements (e.g. GDPR) — especially if source/target or users sit outside the home jurisdiction?
14Is an audit trail of every synced record required for compliance or financial reporting? This is a distinct build item — never assumed to come free with the base sync.
15If the integration touches quoting/pricing, do multiple price books or pricing tiers exist? Multiple price books multiply mapping and testing effort — count as separate scope.
Cross-Cutting Discipline
Verify every use case against the transcript: Label each proposed use case Confirmed / Partially Discussed / Not Discussed before it goes in an SOW.
Distinguish existing automation from new build: If a workflow already exists and the integration just feeds it better data — call it a beneficiary, not a deliverable.
Treat "nice to have" language literally: "If it can be implemented, that'd be great" = mark as optional/stretch-goal in SOW, not a confirmed requirement.
Confirm stated tool boundary: If a stakeholder says "we will only use MuleSoft to insert data" — anything outside that boundary is explicitly out of scope.

Anypoint Platform — Pricing Mechanics
Pricing unit: Flows
Each distinct integration pipeline = one flow. Example: "NetSuite ↔ Salesforce case sync" = 1 flow. Packages include a flow allocation sized to projected need — get the customer's realistic flow count from the discovery checklist before recommending a package.
Flow count traps to avoid
• Bi-directional sync = 2 flows minimum, not 1 — price as two line items
• Multi-company routing (e.g. 1 SF org → 3 QB companies) = base flow + routing layer effort
• Historical backfill = distinct scope item from ongoing incremental sync — price separately
• MuleSoft for Flow — confirm licensing model with datasheet, do not assume same as core Anypoint
